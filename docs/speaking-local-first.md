# SpeakCheck on-device speech pilot

The [Phase 3 runbook](speaking-phase-3.md) covers adaptive structured conversations, Read Aloud, private passage import, review, validation and rollback. The measurements and operational notes below record the earlier pilot baselines.

The pilot is implemented for teacher-selected Practice and Performance Test sessions. It sends transcripts to the existing conversation and evaluation flow. The pilot defaults off. An ordinary session uses its existing server transcription setting.

## Pilot architecture

1. The teacher launches a session with **Use on-device speech recognition (pilot)** and distributes the ordinary code or QR before class. The selected transcription path is saved on the session. The reused activity and its rubric remain portable between runs.
2. Students explicitly prepare the model after joining. The join screen records a short sample, plays it back and runs the recognizer. Readiness requires inference on the sample, a successful authenticated readiness request, a completed model cache, and recognition in at most the greater of six seconds or twice the sample length. A student can notify the teacher that an alternative assessment is needed. Teacher roster reporting is self-reported by the browser.
3. A dedicated Worker lazily loads Transformers.js 3.8.1 and pinned ONNX models through ONNX Runtime Web. The audio engine uses format decoding on the browser, 16 kHz resampling and channel averaging, then transfers the PCM buffer into the worker. It preserves pauses and avoids automatic gain changes in the engine. An energy/variation gate suppresses silence and stationary noise before inference. Recognition can still mistake intermittent noise for words.
4. The model files are cached under `speakcheck-models-v1` using revision-specific URLs. Fully fetched files survive a retry. Partial files can be fetched again. The runtime comes from the same static deployment and is separately cached by the browser. During a turn, a reload first tries the model cache. An incomplete or evicted model returns the student to preparation. The application has a timed worker cancellation path and can retry with a new worker. It uses one WASM thread for managed browsers without cross-origin isolation.
5. The session-bound API authenticates the participant before parsing the dedicated transcript content type. It requires a ready pilot participant and a valid request ID. It accepts up to 8 KiB on the wire and 1,200 transcript characters, uses existing participant and turn limits, and runs normal conversation and evaluation. The same request ID recovers a saved turn without re-transcription or replacement. The browser holds pending audio and the recognized text in memory across transient submission errors and releases it when leaving the session. Refreshing the preparation link uses the existing tab token and roster entry. The avatar pauses rendering during inference, and leaving the activity releases the worker.
6. Turns and exports mark transcripts as device-generated. Provisional text-based feedback stays available. Standalone acoustic criteria such as pronunciation, intonation or oral fluency require teacher review. The normal conversation engine and durable evaluation jobs remain in use. Local sessions limit browser voice synthesis to detected local voices and keep the prompt visible as text.

The engine accepts a recorded Blob or a selected file. Chromium desktop was exercised with WAV and the browser’s microphone capture. MP3, M4A/AAC, MP4, WebM/Opus and Ogg support depends on `decodeAudioData`, the actual codec, and the device. Other formats, damaged copies, background chatter and long compressed files still need a device matrix before implementing assignment uploads. Recognition supplies valid Whisper segment times when available. The app stores no student audio, waveform, confidence percentage, or sample transcription for readiness. The short-fragment uncertainty marker is a heuristic.

## Model comparison

The browser measured three repeated recognitions of one 4.65-second, nine-word Windows-generated English clip on headless Chrome 158, Windows, Intel Core i5-7200U and 8 GiB RAM. WER is the usual word edit distance divided by reference word count. No learner speech was used.

| Candidate | Quantized model assets | Cold / cached model initialization | Inference p50 / p95 | WER |
| --- | ---: | ---: | ---: | ---: |
| Whisper Tiny English q8, WASM | 42,985,755 B | 16.58 s / 2.30 s | 2.69 s / 3.50 s | 0% |
| Whisper Base English q8, WASM | 79,041,253 B | 27.10 s / 2.99 s | 7.75 s / 9.24 s | 0% |
| Moonshine Tiny q8, WASM | 32,079,632 B | 10.01 s / 5.04 s | 0.86 s / 0.97 s | 0% |
| Whisper Tiny English q8, WebGPU | Same weights as WASM | Timed out on this headless configuration | — | — |

These p95 values are the maximum of three observations. Model initialization includes asset reads and ONNX session creation. Cold results also include model downloads. Package size for the production worker is about 0.87 MB uncompressed. The same-origin ONNX runtime includes 21.64 MB of uncompressed WASM and loader files. Cache-only startup fetched zero model bytes. A silent WAV returned no speech. Base supplied an in-range timestamp segment for this clip. Tiny supplied none. None of these observations establishes a proficiency-level or accent accuracy comparison.

The pilot uses Moonshine Tiny q8/WASM based on the smaller download, faster inference, and lower measured post-inference memory. Summed private bytes across the three headless Chrome renderer processes were 86 MB before loading, 524 MB after initialization and 443 MB after inference for Moonshine. Whisper Tiny measured 98 MB, 492 MB and 1,036 MB at the same stages. These single observations include browser overhead and do not measure peak usage or establish an iPad or Chromebook memory budget.

The Whisper q8 ONNX model repositories are Apache-2.0. The upstream Whisper code and weights use MIT. Moonshine Tiny English ONNX is MIT. Unquantized Whisper Tiny and Base ONNX weights alone total about 151 MB and 291 MB, respectively. The diagnostic page keeps both Whisper candidates for accuracy and timestamp comparisons. WebGPU is experimental. [Whisper Tiny ONNX files](https://huggingface.co/Xenova/whisper-tiny.en/tree/main/onnx) · [Whisper Base ONNX files](https://huggingface.co/Xenova/whisper-base.en/tree/main/onnx) · [Moonshine Tiny ONNX files](https://huggingface.co/onnx-community/moonshine-tiny-ONNX/tree/main/onnx) · [Whisper model card](https://github.com/openai/whisper/blob/main/model-card.md) · [ONNX Runtime Web](https://onnxruntime.ai/docs/get-started/with-javascript/web.html) · [Transformers.js WebGPU](https://huggingface.co/docs/transformers.js/en/guides/webgpu)

## Server benchmark

The comparison exercised the ordinary binary route and the pilot transcript route on one local in-memory server with mock providers, 40 participants on loopback, and a 205,278-byte synthetic PCM WAV. An entire phase was started together for the burst run. Each case used a separate session. The upload bytes represent WAV traffic and overstate the expected bandwidth of compressed browser recordings. These are HTTP round trips. Turn timings omit microphone and browser inference. Finish timings measure evaluation admission. All results were available at the first poll in both cases.

| Metric | Ordinary audio route | On-device transcript route |
| --- | ---: | ---: |
| Join round trip p50 / p95 | 193 / 200 ms | 285 / 293 ms |
| Readiness round trip p50 / p95 | — | 52 / 64 ms |
| First-turn HTTP p50 / p95 | 181 / 205 ms | 117 / 157 ms |
| First-turn HTTP p50 / p95 with staggered requests | 7 / 14 ms | 6 / 7 ms |
| Finish admission p50 / p95 | 187 / 189 ms | 140 / 143 ms |
| First-turn request bodies for the class | 8,211,120 B audio | 2,271 B transcript JSON |
| Mock provider operations | 190 including 70 transcriptions | 120 including 0 transcriptions |
| Completion and failed requests | 40/40 and 0/246 | 40/40 and 0/286 |

Each run included 70 successful turns, 10 Help calls, 40 evaluations and five valid idempotent retries. Mock providers made zero external requests. The theoretical count for one student with `T` successful turns and `H` Help calls is `2T + H + 1` on the ordinary external path and `T + H + 1` in a pilot with explicitly permitted external conversation/evaluation. Across 40 students who each give five answers without Help, that is 440 versus 240 nominal external calls before retries or schema recovery. Audio uploads from the pilot are zero.

An instrumented rerun across both routes, with burst and staggered traffic, consumed 2.09 CPU-seconds on the local mock API over 7.20 seconds of elapsed time. Server RSS was about 110 MB at the end. Live provider and database latency, independent conversation response and exact final evaluation latency, GPU memory, server CPU under a real provider, classroom completion and WER for Japanese learners remain unmeasured. Browser inference and server numbers above cannot be added and treated as a measured end-to-end student turn.

A separate benchmark used the normal API entry point, mock providers and local PostgreSQL 18.4. The pilot accepted all 40 simultaneous transcript turns, completed 40 evaluations and had zero failed requests out of 286. Pilot first-turn HTTP latency was 663 ms median and 667 ms p95. Join and finish admission p95 were 1,073 ms and 1,629 ms. All five idempotent retries returned the original turn pair. The ordinary route admitted 16 of 40 simultaneous first-turn WAV uploads and returned 24 HTTP 429 responses at the existing upload cap. These runs exercised database persistence and admission with simulated clients. Inference, classroom networks and hosted database latency require separate measurements.

## Deployment and rollback

Local PostgreSQL 18.4 accepted all 23 migrations on a clean database and the pilot migration on a database with the previous 22 migrations and synthetic historical SpeakCheck records. After upgrade, the session, participant, turn and evaluation matched their previous values apart from the expected defaults for the new fields. The existing evaluation-recovery SQL regression also passed.

The opt-in PostgreSQL integration test uses the regular API startup path, mock providers and a new synthetic account. It verifies that an API restart preserves a paused pilot session and readiness, that resubmitting a request returns the saved turn or completes the missing reply, and that the recovery scan completes an evaluation with an expired lease. A second restart with the pilot disabled verifies that new pilot launches and transcript submissions are rejected and saved results are still readable. Run it using a migrated, disposable loopback PostgreSQL database:

```powershell
$env:SPEAKCHECK_TEST_DATABASE_URL = '<disposable loopback PostgreSQL connection URL>'
node node_modules/tsx/dist/cli.mjs --test apps/server/src/speakingLocalPostgres.integration.test.ts
```

API startup invokes the installed Prisma CLI with the current Node executable. The build must include Prisma, as it does with the documented Render `npm ci --include=dev` command. The local migration and restart checks use disposable databases. Hosted staging still needs its own run with the intended database version, pooler and transport.

| Setting | Scope | Meaning |
| --- | --- | --- |
| `SPEAKING_LOCAL_TRANSCRIPTION_ENABLED=true` | API | Enables teacher opt-in for new sessions and accepts existing pilot turns. Defaults off. |
| `SPEAKING_LOCAL_TRANSCRIPTION_ALLOW_EXTERNAL_AI=true` | API | Permit explicitly approved conversation, Help and evaluation adapters for the pilot. Default off admits the mock provider trio only. The setting records an operator decision and provides no provider or school authorization. |
| `VITE_SPEAKING_LOCAL_DIAGNOSTICS=true` | Web build | Expose standalone `/speak/prepare` for diagnostics before inviting students. The join flow has its own preparation screen for pilot sessions. |
| `VITE_SPEAKING_MODEL_HOST` | Web build | Optional school-approved HTTPS mirror for the pinned model tree. Serve `<model>/resolve/<revision>/<file>` using the files listed in the pinned manifest. Credentials and personal data belong outside the URL. |

1. Use the existing staging or local test environment with `SPEAKING_MOCK_MODE=true` and the pilot flag. Apply the additive Prisma migration using `npm run prisma:deploy` against the intended database. For development without a database, the in-memory repository works.
2. Build the web client and API together. Keep both flags off in production while qualifying the devices. If using a model mirror, verify its CORS and permitted HTTPS origins in the school network. The static runtime files are served with the web app.
3. For planned rollback, stop launching pilot sessions and close their classroom runs after students finish. Then clear `SPEAKING_LOCAL_TRANSCRIPTION_ENABLED` and restart the API. For emergency rollback clear it immediately. Active pilot submissions fail closed, with existing turns and results retained. Existing assessment jobs may finish when their provider permission is still enabled. Clear the external AI permission independently to prevent further processing of pilot evaluations by external providers.
4. The additive migration can remain applied. Before rolling back to a server version that predates the pilot, end pilot runs to preserve their original processing policy. Create a new session for an explicitly allowed alternative.

## Privacy, fairness and operating limits

- An accepted transcript is bound to the session, participant and request. Students have no transcript-edit action. A modified browser can still submit fabricated text or readiness. Provisional results need teacher confirmation. Formal evidence collection needs a separately authorized design.
- Model hosting delivers public assets and sees ordinary connection metadata. It receives no audio, transcript, participant token, or textbook passage. With an approved external provider, conversation and evaluation prompts include transcript content. Existing application retention applies to text and results.
- The public Gemini Developer API terms disallow applications directed to or likely to be used by under-18s. The unpaid terms also allow product improvement and human review of inputs and outputs. Using on-device transcription alone leaves the conversation/evaluation portion subject to those terms. Treat the existing Gemini classroom configuration as a deployment blocker for minors. OpenAI’s API guidance has separate under-18 safeguards and calls for Zero Data Retention before processing personal data of children under 13 or the applicable age of digital consent. No configured cloud adapter has been verified for this school cohort. - Incremental recurring service fees for the local/mock pilot are $0 at existing capacity. No additional service, paid tier, or billing upgrade is configured. Forty cold Moonshine preparations can fetch about 1.28 GB of pinned model assets and 0.90 GB of runtime and worker assets before HTTP compression and reuse. Stage preparations across classes and check existing static hosting and school bandwidth. GitHub Pages documents a 100 GB/month soft bandwidth limit and 1 GB published site limit. Free Render web services can spin down, and incidental usage remains subject to their documented limits. Supabase Free lists 500 MB of database, 1 GB of file storage, 5 GB egress and 5 GB cached egress. The pilot adds a few small database fields and no stored audio. ## Classroom qualification guide

1. Prepare one expendable mock activity. Share its QR before the lesson and record device model, OS, browser, network and Model/Runtime sizes. Capture cold and cached times separately. Use `/speak/prepare` to compare all candidates using de-identified approved clips and reference transcripts. Do not export personally identifiable content from diagnostics.
2. Start with actual managed Chromebooks, iPads and Windows devices. Check microphone permission, playback and the local browser voice. Try a denied microphone, noisy room, unsupported format, interrupted model download, forced WASM, storage exhaustion and a cache-clearing reboot. A desktop-sized emulator is only a layout check.
3. Repeat with 35–40 devices on the school network. Time cold preparation, staged preparation, recording, worker inference, round-trip submission and final evaluation. Record completion and failed requests by phase. With sufficient samples report count, median and p95 by device type, browser and backend. Compare error rates across proficiency groups using manually checked transcripts. Include short replies, quiet speakers and common Japanese learner vowel and consonant patterns. Have teachers judge harms from substitutions and missed responses.
4. Pause, interrupt Wi-Fi, retry a turn after losing its reply, refresh during setup and restart the API. Verify saved transcript history, duplicate turn suppression, readiness recovery and evaluation recovery. Audio and unsent transcripts can be lost after a refresh. Keep recordings tab-local unless a later authorized workflow defines retention.
5. Run `npm run speaking:load` against a disposable open session with `SPEAKING_LOAD_CODE`, `SPEAKING_LOAD_TEACHER_TOKEN`, `SPEAKING_LOAD_START_SESSION=true` and optionally `SPEAKING_LOAD_TRUE_BURST=true`. For the pilot use `SPEAKING_LOAD_LOCAL_TRANSCRIPT=true`. For the ordinary path use `SPEAKING_LOAD_AUDIO_FILE` and optionally `SPEAKING_LOAD_AUDIO_MIME`. Use a synthetic audio fixture with mock providers. The script reports median, p95, failures, duplicate consistency and body bytes. Use the existing `speaking:latency` separately only where a provider and recordings are approved.
6. The optional `speaking-local.spec.ts` browser smoke needs a non-personal WAV of “I like reading books.” in `SPEAKING_E2E_WAV`, a mock API with the pilot enabled and the built web app. Run `npm run test:e2e -w @quizstrike/web -- speaking-local.spec.ts --project desktop-chrome`. The model download is real, and the recording uses Chrome’s synthetic microphone. Measure browser native memory through the browser process or OS task manager and server CPU/RSS through the hosting metrics across the same load phases.

Pilot thresholds and all cohort evidence should be reviewed with teachers before expanding deployment. A passing synthetic smoke supports a technical pilot. Live learner accuracy and classroom completion determine eligibility for wider use.

## Phase 2 structured conversation baseline

The experimental structured conversation mode uses on-device Moonshine transcription and deterministic conversation, Help and assessment rules in the SpeakCheck API. The teacher can reuse an activity's opening and the first two stated success conditions or provide a question script when launching. The server snapshots each script in the session and withholds its concept cues from participant responses. Topic plans and replies survive an API restart through persisted turns and the existing idempotent request handling. Legacy open conversation stays available in deployments that opt to permit it.

### Structured session configuration

| Setting | Effect |
| --- | --- |
| `SPEAKING_STRUCTURED_ENABLED=true` | Allows teachers to opt into a structured session. The mode requires on-device readiness and its transcript content type. Defaults off. |
| `SPEAKING_PROVIDER_INDEPENDENT_ONLY=true` | Blocks active legacy and cloud-assisted Speaking operations and permits the application to boot without AI keys. In this configuration, enable `SPEAKING_STRUCTURED_ENABLED` for new Speaking sessions. Existing results remain readable and pending legacy evaluations remain queued. Defaults off. |

The structured mode always bypasses external transcription, conversation, Help and evaluation adapters, including on mixed deployments that configure Gemini for other sessions. Browser voice playback uses local system voices. Public model asset downloads remain separate from student data. Practice recordings stay on the device. Transcripts and provisional results go to the SpeakCheck API and database.

To specialize an activity, enter up to six lines in **Questions and objectives**, using question, observable objective, comma-separated concept cues, and an optional follow-up separated by vertical bars. Use `@question` in the cues field when the learner should ask a question. Example:

```text
What do you like to read? | State a reading preference | like book, like manga | Can you give one example?
What would you like to ask me? | Ask a question | @question
```

Cues recognize word groups in flexible order and common equivalents such as “enjoy” and “like”. Comma-separated alternatives allow multiple valid answers. An unclear answer can receive one clarification before proceeding. A matching response can trigger the teacher-authored follow-up. Difficulty controls the default prompts and whether the learner is invited to ask a question. Broader or unexpected answers can advance with unconfirmed evidence. When the last prompt is handled, the partner invites the student to finish.

The initial rules identify covered objectives and question form. A fully supported task criterion can receive a 4, and clear question evidence can support the interaction criterion. If evidence for the full objective set is missing, task achievement remains N/A with available evidence cited. Acoustic qualities, language control, speech quality and custom criteria stay for teacher review. Transcript evidence remains provisional. Elementary answers, paraphrases, negation and recognition artifacts need teacher review. The rules make no equivalence claim against a generative evaluator.

The implementation avoids a second model download for semantic matching. A possible later candidate is quantized English MiniLM for intent or paraphrase proposals, with the deterministic state machine and teacher review still controlling decisions. Compare false matches for short and negated learner answers, RAM, cold/cache startup, and added network transfer before considering it. [MiniLM model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2)

Apply the additive structured-session migration in a disposable environment first. To stop new structured sessions and their turns, clear `SPEAKING_STRUCTURED_ENABLED` and restart. Already accepted structured evaluations are deterministic and may settle. Keep `SPEAKING_PROVIDER_INDEPENDENT_ONLY` enabled if the environment must continue to block other modes. No paid service was added.

### Authorized learner benchmark

Enable `VITE_SPEAKING_LOCAL_DIAGNOSTICS=true` in an isolated build and open `/speak/prepare`. Select Moonshine Tiny, Whisper Tiny or Whisper Base and choose automatic, WASM or WebGPU. Load the model and test cache-only startup separately. Choose an authorized clip of up to 32 seconds and enter its manually verified transcript, including audible repetitions and fillers. Label classroom background noise separately. For hallucination checks use a verified no-speech control, including quiet and classroom noise examples. Each run reports latency, duration, word error rate and edit counts, missed speech, speech detected in a control, and lexical filler and adjacent-repeat counts. Counts reflect what the engine rendered as words. They provide no acoustic measure of hesitation.

The JSON export contains only measurements, browser metadata, and model and cache details. It omits audio, filenames, words and references. Use grouped results by model, browser, hardware, clip length and environment. Compare per-clip rates and corpus WER using summed errors divided by summed reference words. Keep no-speech controls out of the WER denominator and report their false-positive rate separately. Repeat authorized clips across models, including short answers, longer answers up to 32 seconds, beginner speech, pauses, alternative wording and background noise. Establish missed-speech and hallucination rates with teachers before selecting a default for general use.

The student preparation screen now offers **Check saved model**. This cache-only path checks readiness without requesting missing model weights. A missing or evicted cache shows the preparation action and Japanese help. Use it before class, retry interrupted downloads so completed files can be reused, and stage cold preparations in small groups. The existing roster reports readiness and alternative assessment requests.

Forty cold Moonshine preparations project about 1.28 GB of model traffic and about 0.90 GB of runtime and worker assets before reuse and compression. Forty complete model cache hits project zero model-asset transfer. Runtime, application and status traffic can still occur. These are projections based on measured single-device asset sizes and observed cache-only model loading. The school-network comparison still requires 40 representative devices in both conditions using controlled cache profiles, elapsed-time measurements, request failures and access-point totals.
